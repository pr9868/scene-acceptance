Runtime, input limits and scale controls

The released harness used for the dairy case had a fixed 10,000-prim admission limit. The larger trial used a development build with caller-selected limits. It rejected an over-budget input as insufficient evidence rather than silently assessing a subset.

These controls tested the development build. The final-mesh fault helps check that a large input is not being truncated. Selected controls do not establish a general scalability guarantee. Detailed packs retain their own image, geometry and sample limits. Native instanceable content and other unsupported composition features remain outside the reader’s supported subset.

The repaired distribution-centre evaluation took about 75 seconds and 1.71 GB peak process memory on the recorded host. That is one run against its selected scope, not a benchmark against another evaluator or a renderer-performance measurement.

What can be reproduced from this collection

The public harness contains the released implementation and its examples. The dairy used release 0.5.0. The larger trial’s development runtime, custom pack and complete deliveries are not included here. The original dairy rejection snapshot is unavailable.

This collection provides the issued briefs, selected results and measurements, repair correspondence, display images and one explanation video. It lets readers inspect the reported findings and comparison, but cannot reproduce either complete original build. No replay command is offered for missing inputs.

The images are display derivatives of retained RTX captures or report excerpts. The video is the producer’s original Blender Cycles explanation. Source-byte hashes in the distribution manifest establish which retained media was used; they do not turn that media into a physical validation.
