# Scene harness handoff

Use the installed `scene-acceptance` library/CLI. Read [the handoff contract](references/handoff.md) for arguments, source formats and evidence receipts.

1. Identify the saved scene bundle, candidate USD, intended use, any brief sources and the caller's real capture capabilities. Preserve the delivered scene revision. Use `check-3d-app` without `--out` to retain each attempt under `./scene-acceptance-runs/`, or select a project folder with `--run-root`. Return the `storage.summary_report` link and retain failed attempts. Explicit `--out` remains available and must be new. Keep the history folder outside input roots; its records can contain private evidence and are not automatically public or a complete source backup.
2. Run `check-3d-doctor` to inspect installed providers and limits. Use `check-3d-app` for the common JSON envelope, progress and cancellation contract. With a raw brief, call `check-3d-prepare` with an explicitly configured interpreter CLI. Without a brief, omit both: preparation uses the versioned general rubric and makes no model call. Pass a custom rubric when the application has one.
3. Inspect the generated requirements and source quotes, numerical targets/tolerances, routes, unresolved items, `scope.json.evaluation_policy`, `capture-plan.json` and feasibility gaps. General review selects applicable authored areas and discloses exclusions; those exclusions are not passes. Record the actual brief's `source_origin` separately from the interpreter. The model's mapping is a proposal. It may miss or misread requirements; pending mapping is not human approval. Do not silently derive targets from the delivered scene or rewrite a brief to make it pass.
4. Record authorized caller scope approval with `check-3d-approve`, expected scope hash, reviewer and reason. Scope approval is separate from outcome approval. The calling application renders the requested evidence using its own authorized renderer. Follow each request's purpose, view role, target objects, camera constraints/guidance, timestamps and fidelity. Distinct angles require distinct images; share an image only when the frozen requests explicitly permit it. Keep motion cameras fixed. Use close-ups when overview views hide relevant details. Do not launch GPU resources merely because the harness requested images.
5. Create a view manifest and fill `receipt-template.json`. Record unavailable requests and why. Supply honest renderer, camera, time, units, image hashes, covered prims and limitations. Reference images from the brief are desired appearance, not proof of delivered appearance. Schematic renders cannot claim surface-material fidelity.
6. Run `check-3d-evidence` for model-free capture validation. Run `check-3d-run-plan` with the returned plan hash and the chosen mode: `checks`, `judge` or `both`. Only model modes need judge configuration and, when available, paired views/receipt. The harness validates evidence and evaluates the frozen plan; it does not render or reinterpret it.
7. Route the result using the top-level `next_action`. A rejected scope returns exit 3 and `review_specification`, even when the report also contains measured failures. Fix the interpretation before starting a scene-repair loop. Execution or usage errors return 4; a scene rejection returns 2.
8. Report a compact table: scene/revision, check or requirement, evaluator, assessed subjects, outcome, supporting evidence and unassessed scope. Keep measured pass/fail, advisory consistent/concern/unknown, and missing evidence distinct. Link the prepared run and full evaluation reports.

Reuse the same plan for repeat reviews of the same saved scene. For an ordinary repair, use `check-3d-bind` with the expected scope hash; it preserves requirements and selected review criteria without reinterpretation. Check `judge_coverage_drift`: newly applicable material or motion areas missing from the frozen rubric require new preparation/review before judge or combined acceptance. A checks-only pass does not assess those visual areas. Supply fresh plan-bound captures and use `--previous-run` to distinguish repaired findings from unassessed checks. A changed brief/profile needs new preparation and scope review. Explicit runtime migration records reviewer and reason; changed general policy or pack identities produce a new scope hash and policy diff requiring new caller approval. Older scopes without a saved evaluation policy need new preparation. Read the reference before migrating or choosing image comparison limits. If the target renderer supplies an MDL library, use the explicit caller-attestation policy and a receipt bound to the candidate and approved target environment. This does not prove shader compilation or rendered quality, and it cannot clear missing ordinary textures.

Use `--reuse-completed` on initial and replay invocations only when reusing identical evidence/opinions is intended; failed runs need fresh outputs. Preserve prior plans, reports and failed attempts. Do not automatically repair scenes, install plugins, approve requirements or publish results as part of evaluation.

## Optional assumption triage

When the caller requests AI help deciding which declared decisions need human review, read [the triage handoff](references/triage.md). This is a separate text-based operation after declared-scope assessment. It does not add a visual question, discover hidden assumptions or supply approval. Use caller-owned policy and preserve the distinction between the AI recommendation and the applied gate.

## Experimental assumption audit

Use the separate `audit` operation only when the caller requests questions about undeclared choices. Read [the audit guide](references/audit.md). Audit can compare the brief, saved scene inventory, declared decisions, pinned scripted results and supplied views. Its output is a cited question for a person, never a measured failure or approval. Preserve missing-evidence disclosures and label synthetic controls separately from measured model discovery.
